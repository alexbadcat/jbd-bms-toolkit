# Класичний протокол JBD «DD»

Опис класичного RS485-протоколу JBD/Jiabaida, реалізованого в `jbd_bms.py` і
`jbd_settings.py`. Це протокол BMS першого покоління серії UP (напр.
UP16S010). Новіша «поліглот»-прошивка (UP16S019 rev.2 і подібні) досі відповідає
на DD-читання, але частину сервісних записів вона мовчки ігнорує — дивись
[protocol-es-up.md](protocol-es-up.uk.md) про протокол, яким на ній РЕАЛЬНО
пишуть.

## Формат кадру

```
DD [addr] [action] [cmd] [len] [data...] [crc_hi] [crc_lo] 77
```

- `0xDD` / `0x77` — фіксовані старт/кінець.
- `addr` — адреса пака на шині (`0x00` = майстер/DIP-0000, ненульова — для
  другого пака на спільній шині через Y-розгалуження). **Це розширення
  UP-серії.** Класичний 7-байтовий кадр, який описують деякі джерела
  (`DD A5 03 00 FF FD 77`, без байта адреси) UP16S-серія **мовчки
  відкидає** — завжди шли форму з адресою.
- `action` — `0xA5` = READ, `0x5A` = WRITE.
- `cmd` — номер команди/регістра (див. таблиці нижче).
- `len` — довжина `data` в байтах (0 для більшості читань).
- `crc_hi`/`crc_lo` — контрольна сума, див. нижче.

Кадр відповіді: `DD [addr] [cmd] [status] [len] [data...] [crc_hi] [crc_lo] 77`
(`status == 0` = OK; ненульовий — BMS відмовила/дала помилку).

### Контрольна сума

```
checksum = (0x10000 - sum(байти від addr до кінця data)) & 0xFFFF
```

тобто сума рахується по `addr, action/status, cmd, len, data...` —
**включно з байтом адреси**, пакується big-endian у два байти перед кінцевим
`0x77`. Ця формула має збігатись і в запиті, і у відповіді; кадр із цілим
конвертом `DD...77`, але битою CRC — це биті дані, а не валідна відповідь (чому
це критично на спільній шині з двома паками — дивись
[lessons-learned.md](lessons-learned.uk.md)).

### Повтори запиту

BMS засинає приблизно через 5 хв без обміну по шині (даташит §4.8); перший
кадр після пробудження часто губиться. `jbd_bms.py` повторює запит автоматично
і класифікує причину невдачі (тиша / чужа луна-адреса / обрізаний кадр / бита
CRC / ненульовий статус), а не вважає будь-яку відсутність відповіді фатальною
одразу.

## Два адресні простори в одному форматі кадру

- **Інформаційні команди** (`cmd` 0x03/0x04/0x05) — читаються будь-коли, без
  сервісного режиму. Повертають структурований блок даних (див. «Базовий
  інформаційний блок» нижче).
- **Сервісні/конфігураційні регістри** (`cmd` 0x10-0x31, 0xAD-0xB0+, 0xE0) —
  частина читається без входу в сервісний режим; решта (і всі записи)
  потребують спершу увійти в сервісний режим.

## Сервісний режим (factory mode)

| Регістр | Напрям | Значення | Значення |
|---|---|---|---|
| `0x00` | WRITE | `0x5678` | Увійти в сервісний/factory режим |
| `0x01` | WRITE | `0x0000` | Вийти **БЕЗ** збереження |
| `0x01` | WRITE | `0x2828` | Вийти **ЗІ** збереженням у EEPROM |

Послідовність запису в тулкіті: вхід (`0x00=0x5678`) → запис цільового
регістра → вихід-зі-збереженням (`0x01=0x2828`), завжди у блоці `finally`, щоб
виняток посеред запису не лишив BMS у сервісному режимі. Сесії тільки читання
завжди виходять **без** збереження (`0x0000`), тож чистий дамп нічого не може
змінити — навіть якщо щось пішло не так посеред читання.

## Базовий інформаційний блок (`cmd 0x03`)

| Зсув | Довж | Поле | Масштаб |
|---|---|---|---|
| 0 | 2 | Напруга пакета | ×0.01 В |
| 2 | 2 | Струм (зі знаком) | ×0.01 А, + = заряд, − = розряд |
| 4 | 2 | Залишкова ємність | ×0.01 А·год |
| 6 | 2 | Номінальна (повна) ємність | ×0.01 А·год |
| 8 | 2 | Лічильник циклів | — |
| 10 | 2 | Дата виробництва (сира) | — |
| 12-13 | 2 | Статус балансу, комірки 1-16 (біт на комірку) | — |
| 14-15 | 2 | Статус балансу, комірки 17-32 (біт на комірку) | — |
| 16 | 2 | Бітмаска захистів | див. нижче |
| 18 | 1 | Версія прошивки | старший ніббл `.` молодший ніббл |
| 19 | 1 | SOC | % |
| 20 | 1 | Бітмаска MOSFET | біт0 = заряд, біт1 = розряд |
| 21 | 1 | Кількість комірок | — |
| 22 | 2 | Бітмаска тривог | — |
| 24 | 2 | Температура середовища | 0.1 K (`(v-2731)/10` = °C) |
| 26 | 2 | Температура FET | 0.1 K |
| 28 | 1 | Кількість NTC-датчиків | далі стільки ж пар по 2 байти температур |

⚠️ Грабля з продакшену: байти 12-13 — це комірки **1-16**, байти 14-15 —
комірки **17-32** — читання їх як одне 32-бітне big-endian число замість двох
окремих 16-бітних половинок кладе біти 0-15 не на той діапазон комірок (16S
паки тиждень показували «нема балансування» саме через це).

### Бітмаска захистів (зсув регістра 16, біт → значення)

```
0  перенапруга комірки        7  переохолодження при розряді
1  недонапруга комірки        8  надструм заряду
2  перенапруга пакета         9  надструм розряду
3  недонапруга пакета         10 коротке замикання
4  перегрів при заряді        11 помилка АЦП
5  переохолодження при заряді 12 програмне блокування MOSFET
6  перегрів при розряді
```

## Сервісні регістри (таблиця `REGISTERS` у `jbd_settings.py`)

| Рег | Назва | Одиниця |
|---|---|---|
| `0x10` | Проектна (номінальна) ємність | А·год |
| `0x11` | Ємність циклу | А·год |
| `0x12` | 🔑 Напруга 100% комірки (тригер SOC=100%, див. нижче) | мВ |
| `0x13` | Напруга розрядженої комірки | мВ |
| `0x14` | Саморозряд | сире |
| `0x15` | Дата виробництва | сире |
| `0x16` | Серійний номер | сире |
| `0x17` | Лічильник циклів | сире |
| `0x18`/`0x19` | Перегрів при заряді / відпускання | °C (`(v-2731)/10`) |
| `0x1A`/`0x1B` | Переохолодження при заряді / відпускання | °C — див. примітку нижче |
| `0x1C`/`0x1D` | Перегрів при розряді / відпускання | °C |
| `0x1E`/`0x1F` | Переохолодження при розряді / відпускання | °C |
| `0x20`/`0x21` | Перенапруга пакета / відпускання | В (×0.01) |
| `0x22`/`0x23` | Недонапруга пакета / відпускання | В |
| `0x24`/`0x25` | Перенапруга комірки / відпускання | мВ |
| `0x26`/`0x27` | Недонапруга комірки / відпускання | мВ |
| `0x28`/`0x29` | Надструм заряду / розряду | А (×0.01) |
| `0x2A` | 🔑 Старт балансування (напруга комірки) | мВ |
| `0x2B` | 🔑 Вікно балансування (поріг дельти) | мВ |
| `0x2C` | Затримка перенапруги пакета | мс |
| `0x2D` | 🔑 Бітмаска `FuncConfig` — див. нижче | сирі біти |
| `0x2E`/`0x2F` | Затримка перенапруги / недонапруги комірки | мс |
| `0x30`/`0x31` | Затримка надструму заряду / розряду | мс |

⚠️ Регістри `0x1A`/`0x1B` («переохолодження при заряді») використовують
**сирі одиниці 0.1 K**, а не °C напряму: `2731 = 0 °C`, `2781 = 5 °C`. LFP-
комірки не повинні заряджатися нижче 0 °C (ризик плейтингу літію) — заводські
дефолти приблизно `−5/0 °C` часто піднімають до `0/+5 °C` для запасу безпеки.

⚠️ **Регістри від `0x32` і далі — НЕ налаштування**, а дзеркало миттєвих
напруг комірок (регістр `0x32` віддавав живу напругу комірки 3 в момент
читання). `jbd_settings.py` навмисно зупиняє читання таблиці на `0x31`, щоб не
видавати живу телеметрію за «параметр».

### Біти `0x2D` FuncConfig

| Біт | Значення |
|---|---|
| 2 | `balance_en` — балансування увімкнено взагалі |
| 3 | `chg_balance_en` — **обирає режим тригера балансу**: 1 = лише під зарядом, 0 = лише статичний (див. [balancing.md](balancing.uk.md) — це взаємовиключні режими, а не додатковий дозвіл) |
| 4/5 | Біти LED-індикації |
| 12 | Множник одиниці лічильника ємності (впливає на трактування `0xE0` нижче) |

Спостережені робочі/заводські значення: `471` (`0x01D7`, біт3=0, лише
статичний) і `479` (біт3=1, лише під зарядом).

## Регістри калібрування струму (`0xAD`-`0xAF`)

| Рег | Значення |
|---|---|
| `0xAD` | Калібрування нуля струму — писати `0` **лише коли реальний струм ~0 А** |
| `0xAE` | Калібрування струму заряду, одиниці 10 мА — писати **реальний виміряний струм** під час заряду |
| `0xAF` | Калібрування струму розряду, одиниці 10 мА — писати **реальний виміряний струм** під час розряду |

Це **тригерні регістри, не конфігурація**: запис значення каже BMS «реальний
струм ЗАРАЗ дорівнює цьому», і вона перераховує внутрішній gain. Визначеного
read-back для них нема (читання віддає шум/непов'язані дані) — **верифікація
має бути за ефектом**: виміряти струм знову після запису й перевірити, що він
сходиться до цілі (допуск ~0.15 А або 3%, що більше). На залізі з лише
класичним DD вони працюють як задокументовано; на новішій «поліглот»-прошивці
вони підтверджуються (ack=OK), але дають **нульовий вимірюваний ефект** (див.
[protocol-es-up.md](protocol-es-up.uk.md) і [soc-calibration.md](soc-calibration.uk.md)).

## Регістр залишкової ємності (`0xE0`)

`u16`, одиниці 10 мА·год (чинний, коли біт12 `0x2D` = 0). Запис у нього на
рівні DD — аналог дії «Editing capacity» у вендорських утилітах: напряму
переписує лічильник А·год, що використовується для SOC. Як і калібрувальні
регістри, визначеного read-back нема, тож верифікуй за ефектом: перечитай
базовий інформаційний блок (`cmd 0x03`) і перевір `remaining_ah`. BMS
**округлює результат до цілого відсотка** від номінальної ємності (перевірено:
ціль 88.41 А·год проти номіналу 148.5 А·год лягла як 89.09 А·год = рівно 60%).

## Правило SOC=100%

За вендорською документацією (мануал JBDTools): лічильник SOC скидається на
100%, коли **середня** напруга комірок перевищує регістр `0x12` («напруга 100%
комірки») безперервно протягом 5 секунд. Це перевірка саме СЕРЕДНЬОГО, не
покоміркова — якщо точка утримання постійної напруги інвертора сидить трохи
нижче порогу (напр. CV 57.6 В / 16 комірок = середня 3.597 В проти
`0x12 = 3.600 В`), умова скидання **ніколи не виконується**, і лічильник
мовчки дрейфує через облік саморозряду (`0x14`) замість періодичного
перепідв'язування до 100%. Повну діагностику й фікс (невелике зниження `0x12`,
напр. до 3575 мВ) дивись у [soc-calibration.md](soc-calibration.uk.md).

## CLI-використання (`jbd_bms.py`, `jbd_settings.py`)

```bash
# Прочитати все (пакет + комірки), людський вивід
python jbd_bms.py --port /dev/ttyUSB0 --addr 0

# Тільки комірки, машинний вивід
python jbd_bms.py --addr 0 --cells --json

# Дамп усіх відомих сервісних регістрів (спершу читання без сервісного режиму,
# фолбек на сервісний режим тільки для читання, якщо відповіло замало регістрів)
python jbd_settings.py --addr 0

# Дамп + зберегти JSON-бекап (ЗАВЖДИ роби це перед будь-яким записом)
python jbd_settings.py --addr 0 --save backup-before-write.json

# Прочитати довільні/недокументовані регістри (тільки читання, розшифровка dec/hex/біти)
python jbd_settings.py --addr 0 --read 0x12 0x2D 0x3D

# Записати регістр з allowlist (потребує --yes; верифікується свіжим перечитом після save)
python jbd_settings.py --addr 0 --set 0x2A=3400 --yes

# Записати лічильник залишкової ємності (корекція SOC), значення в одиницях 10 мА·год
python jbd_settings.py --addr 0 --set 0xE0=8841 --yes

# Калібрування gain струму заряду (одиниці 10 мА) — ОБОВ'ЯЗКОВО під реальним,
# стабільним зарядним струмом того ж напряму; верифікується виміром струму після
python jbd_settings.py --addr 0 --set 0xAE=590 --yes
```

`--set` приймає лише регістри з явного allowlist інструмента (пороги
балансування, напруга повного/розрядженого, FuncConfig, пороги відпускання,
переохолодження при заряді) плюс особливі випадки `0xE0` (залишкова ємність) і
`0xAD`-`0xAF` (калібрування струму) — все інше навмисно відхиляється.
