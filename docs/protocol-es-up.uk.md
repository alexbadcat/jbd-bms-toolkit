# Протокол ES-UP («поліглот» / Eco-Worthy)

Деякі новіші ревізії прошивки JBD/LS-Battery (тут ідентифіковано на блоці
UP16S019 rev.2 «поліглот») відповідають на класичний [DD-протокол](protocol-jbd-dd.uk.md)
для читання, але **мовчки ігнорують DD-записи** в кілька сервісних регістрів
(напруга 100% `0x12`, калібрування струму `0xAE`/`0xAF` — вони підтверджують
запис як прийнятий, а потім відкочуються при наступному свіжому читанні). На
тій самій RS485-шині ці блоки **ТАКОЖ** розмовляють другим протоколом у стилі
Modbus-RTU — тут його називають за ідентифікаційними маркер-байтами, «ES-UP»
(також трапляється назва «Eco-Worthy») — і саме цим каналом рідна утиліта
вендора реально міняє параметри. Цей протокол реалізований у `esup.py` і
`esup_factory_reset.py`.

Пак, що розуміє лише класичний DD (без «поліглот»-прошивки), на цьому
протоколі взагалі не відповідає, тож ризику колізії при одночасній роботі обох
каналів на одній шині нема, доки кожен пак реагує лише на свою адресу.

## Формат кадру

Той самий фізичний рівень, що й DD: 9600 8N1, та сама RS485-шина, інша адреса
на дроті.

**Читання (код функції `0x78`):**
```
запит:    [addr][0x78][startHi][startLo][endHi][endLo][00][00][crcLo][crcHi]
відповідь: [addr][0x78][start:2][end:2][dlen:2][data...][crc:2]
```

**Запис (код функції `0x79`):**
```
[addr][0x79][start:2][end:2][dlen:2][11 4A 42 44][payload][crc:2]
```
`dlen = 4 (маркер) + len(payload)`. 4-байтовий маркер `11 4A 42 44` («JBD»)
**обов'язковий** — кадри без нього відхиляються.

Усі багатобайтові поля — MSB-first (big-endian), **КРІМ CRC**, яка пакується
LSB-first.

### CRC16

Стандартний Modbus-стиль CRC16: init `0xFFFF`, поліном `0xA001`, результат
пакується little-endian (`struct.pack("<H", crc)`).

```python
def crc16(d: bytes) -> bytes:
    crc = 0xFFFF
    for b in d:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return struct.pack("<H", crc)
```

### Розлочення не потрібне для записів user-рівня

На відміну від танцю з factory-паролем у DD-протоколі, **звичайні ES-UP-записи
(`0x79`) у блоки user-параметрів не потребують НІ пароля, НІ входу в сервісний
режим взагалі** — просто пишеш, і воно одразу застосовується. Це саме той
канал, яким користується рідний софт JBDTools. Єдиний блок, який ЗАЛОЧЕНИЙ за
замовчуванням — калібрувальний `0x3800`, див. «Режим налагодження DV/DP»
нижче.

## Блоки регістрів

### `0x1000` — Статус пакета (телеметрія тільки для читання, 162 байти)

| Зсув | Поле | Масштаб |
|---|---|---|
| +0 | Напруга пакета | /1000 → В |
| +4 | Струм | `(сире - 300000) / 100` → А |
| +8 | SOC | /100 → % |
| +10 | Залишкова ємність | /100 → А·год |
| +12 | Повна ємність | /100 → А·год |
| +14 | Номінальна ємність | /100 → А·год |
| +70..+104 | 16 напруг комірок | /1000 → В, по одному `u16` на комірку |

### `0x1C00` — Користувацькі параметри (пишуться звичайним `0x79`, 136 байтів)

| Зсув | Абс. адреса | Поле |
|---|---|---|
| +4 | `0x1C04` | Старт балансування (`BalanceV`) |
| +6 | `0x1C06` | Вікно балансування (`BalanceDiff`) |
| +12 | `0x1C0C` | Напруга порогу 100% (`FullAdjustV`) — напр. `5760` = поріг 57.60 В пакета |
| +14 | `0x1C0E` | Струм порогу 100% (`FullAdjustC`) — напр. `1500` = 15.00 А |
| +16 | `0x1C10` | Рядок коду BMS (ідентифікатор пристрою) |
| +120 | `0x1C78` | Напруга сну (`SleepV`) |
| +122 | `0x1C7A` | Затримка сну (`SleepDelay`) |
| +124 | `0x1C7C` | **Режим балансування**: `0` = лише під зарядом, `1` = статичний — див. [balancing.md](balancing.uk.md) |
| +126 | `0x1C7E` | Тип протоколу RS485 |
| +128 | `0x1C80` | Тип протоколу CAN |

### `0x2000` — Ємність (64 байти)

| Зсув | Абс. адреса | Поле |
|---|---|---|
| +0 | `0x2000` | Номінальна ємність (÷100 → А·год) |
| +2 | `0x2002` | Повна ємність (÷100 → А·год) |
| +4 | `0x2004` | Залишкова ємність (÷100 → А·год) — **ціль запису для корекції SOC**, див. нижче |
| +6 | `0x2006` | SOC (÷100 → %) |
| +10 | `0x200A` | Лічильник циклів — **запис приймається ЛИШЕ тут** (дзеркала на `0x2000+10`, `0x3900+16` і класичному DD `0x17` — тільки читання/запис ігнорується) |
| +26..+40 | `0x201A`-`0x2028` | Таблиця OCV — 4 точки `(напруга/1000, SOC/100)` — на спостереженому блоці переважно незаповнена/нулі |
| +52 | `0x2034` | `RSNS` (константа, пов'язана з шунтом), спостережено `210` |

### `0x3800` — Калібрувальні gain-коефіцієнти (32 байти, **залочено на запис за замовчуванням**)

База `10000` = gain ×1.0000.

| Зсув | Поле | Заводське значення (спостережено) |
|---|---|---|
| +0 | Gain струму заряду | `10460` |
| +4 | Gain струму розряду | `10452` |
| +8..+38 | 16 gain-коефіцієнтів вимірювання напруги комірок (по `u16` на комірку 1..16) | `~10006`-`10028` |

### `0x3900` — Дзеркало заводських порогів (32 байти, довідково, тільки читання)

Спостережено: `BalanceV 3300`, дельта балансу, налаштування сну,
`FullAdjustV 5680`, `FullAdjustC 1500`, друга напруга порогу 100% `5760` на
зсуві +58.

## Режим налагодження DV/DP (потрібен для запису `0x3800`)

Запис у калібрувальний блок `0x3800` у звичайному робочому режимі
підтверджується (`ack=OK`), але **не дає ефекту** — читання після нього
показує незмінене значення. Блок реально приймає записи, лише коли BMS
переведена в режим «Design Verification / Design Parameter» (DV/DP,
налагодження):

```
запис 0x2900 = 0x5A02   # увійти в режим DV/DP (налагодження)
...запис у блок 0x3800...
запис 0x2900 = 0x0000   # повернутись у звичайний режим
```

`0x5A01` (режим «Tooling») цей блок **НЕ** розлочує — лише `0x5A02` (DV/DP).
Персист підтверджено на свіжій сесії читання (переживає закриття й повторне
відкриття serial-з'єднання); чи переживає він фактичний цикл живлення самої
BMS — окремо не перевірено.

### 🔑 Ключова знахідка: адресація запису всередині `0x3800` — ІНДЕКСНА u16, не байтова

У режимі DV/DP кадр запису на адресу `0x3800 + k` лягає в **офсет даних
`2k`** всередині блоку — тобто адреса запису є індексом у масиві значень
`u16`, а не байтовим офсетом, як у всіх інших блоках цього протоколу.
Конкретно:

| Адреса запису | Лягає в офсет даних | тобто |
|---|---|---|
| `0x3804` (k=4) | +8 | gain-коефіцієнт комірки №1 |
| `0x3808` (k=8) | +16 | gain-коефіцієнт комірки №5 |

Читання (`0x78`) того самого блоку — звичайне, байт-адресоване — лише
**записи** у режимі DV/DP використовують цю подвоєну індексацію.

Це спричинило реальний інцидент: запис, покликаний налаштувати «gain струму
розряду» (байтовий зсув +4, що при байтовій адресації відповідало б адресі
`0x3804`), насправді пішов на правильно обчислену індексну адресу, але
РАНІШЕ ручна спроба з наївною байтовою адресацією лягла на зсув +8 —
мовчки зіпсувавши gain-коефіцієнт вимірювання напруги комірки №1
(`10006 → 10452`, через що BMS показувала комірку №1 приблизно на +4.5%
завищеною, що спрацьовувало як хибний захист). Спочатку це виглядало як
замок на боці вендора (підтверджено як «заблоковано» навіть рідним
JBDTools, який теж відмовлявся перекалібрувати по RS485), поки не
ідентифікували описану вище поведінку адресації й не записали правильний
коефіцієнт назад через правильно обчислену індексну адресу. Повну історію
дивись у [lessons-learned.md](lessons-learned.uk.md) і
[balancing.md](balancing.uk.md#кейс-комірки-1).

Хелпер, що обчислює правильну адресу запису для заданого офсету даних:

```python
def gain_write_addr(data_off: int) -> int:
    return 0x3800 + data_off // 2
```

## Командні регістри (дії, не збережені дані — під `0x29xx`)

| Адреса | Значення запису | Дія |
|---|---|---|
| `0x2900` | `0x5A02` / `0x0000` | Увійти / вийти з режиму налагодження DV/DP |
| `0x2902` | — | Керування MOS |
| `0x2908` | — | Сон |
| `0x290C` | `0x55AA` | Відновити заводські параметри |
| `0x290E` | `0x5A5A` | Factory reset |
| `0x2912` | `0x44AA` | Перезавантаження |

⚠️ Factory reset (`0x290E`) сам по собі **не виправляє** збитий калібрувальний
коефіцієнт і може заразом скинути інші user-поля до заводських значень.
`esup_factory_reset.py` обгортає це безпечно:

1. Бекапить блоки `0x1000`, `0x1C00`, `0x2000`, `0x3800`, `0x3900` у файли.
2. Виконує reset (лише з `--yes`; інакше — сухий прогін, що просто друкує
   план).
3. Звіряє diff кожного блоку з бекапом до reset.
4. Автоматично відновлює відомі user-поля, що змінились (`FullAdjustV`,
   `FullAdjustC`, `BalanceV`, `BalanceDiff`, номінальна/повна ємність) до
   значень до reset через звичайні ES-UP-записи.
5. Звітує, що змінилось і що відновлено.

## Використання бібліотеки (`esup.py`)

`esup.py` — бібліотечний модуль (без CLI). Ключові функції:

```python
import esup

# Калібрувальні gain струму (база 10000 = ×1.0000)
esup.read_gains(port, addr=1)                      # {"charge": ..., "discharge": ...}
esup.set_gain(port, esup.GAIN_CHARGE, 10303, addr=1)   # обгорнуто DV/DP + перевірка персиста

# Gain вимірювання напруги комірки, cell_no 1..16
esup.set_cell_gain(port, cell_no=1, value=10006, addr=1)

# Ємність / SOC
esup.read_capacity(port, addr=1)                    # nominal/full/remaining А·год + soc %
esup.set_remaining_ah(port, ah=143.9, addr=1)        # корекція SOC, див. soc-calibration.md

# Низькорівневе
esup.read_block(ser, start, end, addr=1)             # сирі байти
esup.write_reg(ser, start, end, payload, addr=1)     # сирий ack-кадр або None
```

CLI `esup_factory_reset.py`:

```bash
# Сухий прогін: лише читає й бекапить, друкує план
python esup_factory_reset.py

# Реально виконати factory reset + авто-відновлення
python esup_factory_reset.py --yes
```

## Що НЕ працює на цій прошивці

- **Сервісні записи DD-протоколу** в регістр `0x12` (напруга 100%)
  підтверджуються як прийняті, але **не персистяться** — свіжий перечит після
  нової сесії показує незмінене старе значення.
- **Калібрувальні регістри DD `0xAD`-`0xAF`** підтверджуються як прийняті з
  **нульовим вимірюваним ефектом** на показаному струмі.
- Рідний софт JBDTools, по тій самій RS485-лінії, теж **не може**
  перекалібрувати збитий gain комірки напряму (видавав китайськомовну помилку
  «calibration failed») — це не обмеження саме цього тулкіта.
