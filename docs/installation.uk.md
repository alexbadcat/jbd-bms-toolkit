# Інструкція з розгортання

Покрокове розгортання `jbd-bms-toolkit`: читання JBD/Jiabaida LiFePO4 BMS по
RS485, міст у MQTT/Home Assistant і (опційно) тюнінг балансування та
ємності. Кожна команда нижче — копіпаст-готова і відповідає РЕАЛЬНИМ CLI-
прапорцям скриптів (`--help` теж завжди працює).

## 0. Що потрібно

**Залізо**

- JBD/Jiabaida BMS серії «UP» (тулкіт зроблено й перевірено на UP16S010 і
  UP16S019 rev.2 «поліглот»; інші моделі серії UP, що говорять тим самим
  DD-кадром, мають працювати для читання — дивись
  [protocol-jbd-dd.uk.md](protocol-jbd-dd.uk.md)).
- USB-RS485 адаптер. Рекомендовано на чіпі FTDI (udev-правило в
  `deploy/udev/99-rs485.rules` написане під vendor/product ID FTDI —
  підправ, якщо в тебе інший чіп, напр. CH340).
- Кабель від адаптера до порту **RS485** на BMS (НЕ «Parallel»/«UART», якщо
  на BMS кілька RJ45-портів — розпіновку RS485 бери з даташита своєї моделі;
  розпіновка для UP16S010 наведена як орієнтир у docstring `src/jbd_bms.py`,
  але **звір зі своїм даташитом** — розпіновки різняться між партіями JBD).
- Linux-хост для моста: Raspberry Pi, NAS, невеликий сервер або VM — будь-що,
  що тримає USB-пристрій і виконує Python 3.9+.
- MQTT-брокер (напр. Mosquitto), доступний з того хоста.
- Home Assistant з налаштованою MQTT-інтеграцією на той самий брокер (щоб
  MQTT-discovery сам підхопив сутності).

## 1. Підключення шини

- З'єднай лінії A/B USB-RS485 адаптера з пінами A/B на RS485-порту BMS, і
  GND з GND. Термінацію/bias-джампери адаптера лиши за замовчуванням, якщо
  нема проблем із сигналом на довгій лінії.
- Швидкість задана прошивкою BMS: **9600 бод, 8N1**. Жоден зі скриптів тут не
  має прапорця зміни швидкості — якщо BMS не відповідає на 9600, це проблема
  підключення/адреси, а не швидкості.
- **Адреса пака**: кожна BMS на шині ідентифікується адресою, зазвичай через
  DIP-перемикач або джампер-блок на самій BMS (дивись мануал своєї моделі; на
  серії UP `0000` зазвичай = адреса 0, дефолтний «майстер»). Якщо в тебе один
  пак — лиши адресу за замовчуванням (0), `BMS_ADDRS`/`--addr` чіпати не
  треба взагалі.
- **Кілька паків паралельно**: підключи RS485-порт кожного пака до тієї самої
  шини (Y-розгалуження на зовнішньому розʼємі підходить — це спільна
  multidrop-шина, не точка-точка), і вистав кожному паку СВОЮ окрему адресу
  через DIP до підключення. Запамʼятай, яка адреса — «класичний DD», а яка —
  «ES-UP/поліглот»: дивись крок 7 і
  [protocol-es-up.uk.md](protocol-es-up.uk.md), чому це важливо саме для
  запису (не для читання).

## 2. Встановлення

```bash
git clone <url-цього-репо> jbd-bms-toolkit
cd jbd-bms-toolkit
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Якщо ще й тести ганятимеш:

```bash
pip install -r requirements-dev.txt
```

## 3. Перше читання — перевір підключення й адресу

Поки демон ЩЕ НЕ запущений (ніхто інший не повинен тримати порт):

```bash
python3 src/jbd_bms.py --port /dev/ttyUSB0
```

Виведе зведення по пакету (напруга, струм, SOC, ємність, температури,
захисти) і всі напруги комірок. Якщо бачиш «немає відповіді» — перевір
полярність A/B (найчастіша помилка — переплутані місцями), GND, адресу DIP, і
що кабель саме на RS485-розʼємі (не «Parallel»).

Якщо не знаєш, на яку адресу відповідає пак, або взагалі не впевнений у
протоколі — проскануй:

```bash
python3 src/bms_probe_multi.py
```

Це фіксований скан (без CLI-прапорців), пробує класичний DD, DD з адресою,
Modbus RTU (функції 3/4) і PACE/Seplos ASCII-пробу на швидкостях 9600/19200/
115200 і друкує будь-яку сиру відповідь. Шину пробує лише коли реально
запущений (звичайний `if __name__ == "__main__"`-гард є, як і в інших
скриптах тут). Зміни константу `PORT` на початку файлу або виставляй
env `BMS_PORT`, якщо адаптер не `/dev/ttyUSB0`.

Коли адреса відома, перевір кожен пак окремо:

```bash
python3 src/jbd_bms.py --port /dev/ttyUSB0 --addr 1 --json
```

## 4. Бекап налаштувань ПЕРЕД будь-якими змінами

**Перед будь-яким записом** — зроби дамп і збережи поточні сервісні регістри,
це твій відкат, якщо запис піде не так:

```bash
python3 src/jbd_settings.py --port /dev/ttyUSB0 --addr 0 --save backup-pack0.json
python3 src/jbd_settings.py --port /dev/ttyUSB0 --addr 1 --save backup-pack1.json
```

`jbd_settings.py` без `--save`/`--set`/`--read` просто друкує розшифровані
регістри на екран. Тримай ці бекапи десь поза робочою текою репо.

## 5. Конфіг і ручний запуск

```bash
cp jbd2mqtt.env.example jbd2mqtt.env
$EDITOR jbd2mqtt.env
```

Заповни щонайменше `MQTT_HOST`, і якщо адреса пака не 0 — `BMS_ADDRS`
(через кому, напр. `BMS_ADDRS=0,1`). Усі змінні, які читає тулкіт (MQTT,
серійний порт, слідкувач балансування, HA REST API для опційних
аналітичних скриптів) — у коментарях `jbd2mqtt.env.example`.

Спершу запусти на передньому плані з кореня репо, щоб одразу бачити помилки:

```bash
cd src && python3 jbd2mqtt.py
```

В іншому терміналі перевір, що дані йдуть у MQTT:

```bash
mosquitto_sub -h <MQTT_HOST> -u <MQTT_USER> -P <MQTT_PASS> -t 'deye_bms/#' -v
mosquitto_sub -h <MQTT_HOST> -u <MQTT_USER> -P <MQTT_PASS> -t 'homeassistant/#' -v   # discovery-конфіги, раз при конекті
```

Далі перевір Home Assistant: з увімкненим MQTT-discovery новий пристрій
(«Батарея Deye (BMS)» або подібна назва для додаткових паків) має зʼявитись
у **Settings → Devices & Services → MQTT** за кілька секунд після конекту
моста, одразу з усіма сутностями комірок/напруги/струму/температур/балансу —
жодних ручних визначень сутностей у `configuration.yaml` не треба. Зупини
передній план (Ctrl-C), коли переконався.

## 6. Запуск як сервіс

**systemd** (рекомендовано для Pi/сервера/NAS):

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin jbd2mqtt
sudo mkdir -p /opt/jbd-bms-toolkit
sudo cp -r . /opt/jbd-bms-toolkit/
sudo cp jbd2mqtt.env /opt/jbd-bms-toolkit/jbd2mqtt.env   # твій заповнений конфіг
sudo chown -R jbd2mqtt:jbd2mqtt /opt/jbd-bms-toolkit

# Якщо ставив залежності у venv, а не в системний Python — спершу
# відредагуй ExecStart у юніті нижче на python3 з того venv.
sudo cp deploy/systemd/jbd2mqtt.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now jbd2mqtt.service
```

Перевір, що живий, і дивись логи:

```bash
sudo systemctl status jbd2mqtt.service
sudo journalctl -u jbd2mqtt.service -f
```

**Стале імʼя пристрою (udev)**: `/dev/ttyUSB0` може мовчки перенумеруватись
після ребуту чи переткнення USB, якщо адаптерів кілька. Постав
`deploy/udev/99-rs485.rules` (інструкція в коментарях файлу — знайди
`idVendor`/`idProduct` свого адаптера через `udevadm info`, поклади правило в
`/etc/udev/rules.d/`, перезавантаж правила), щоб отримати стабільний
`/dev/rs485-bms`, і виставляй `SERIAL_PORT=`/`BMS_PORT=` у `jbd2mqtt.env` саме
на нього.

**Docker** (альтернатива systemd): `deploy/docker/Dockerfile` +
`deploy/docker/docker-compose.yml` збирають і запускають міст у контейнері з
прокинутим `/dev/ttyUSB0` через `devices:`. Конфіг іде змінними середовища
(`env_file: jbd2mqtt.env`), бо авто-підхоплення `.env`-файлу шукає його лише
поряд зі скриптом на диску. Спершу підправ `devices:` під свій реальний шлях.

## 7. Слідкувач режиму балансування

Пасивний балансир BMS має два взаємовиключні режими — «балансувати лише під
зарядом» і «балансувати в спокої» — і активний лише один (фізика й чому це
важливо — [balancing.uk.md](balancing.uk.md)). `BalanceModeFollower` з
`balance_mode.py`, підключений у головний цикл `jbd2mqtt.py`, стежить за
напругою комірок і струмом кожного пака й перемикає режим автоматично, з
гістерезисом і обмеженою частотою записів, щоб не зносити EEPROM BMS.

Він УВІМКНЕНИЙ за замовчуванням. Вимкнути без правки коду:

```bash
# у jbd2mqtt.env
BALANCE_MODE_FOLLOW=0
```

Якщо на одній шині є паки і на класичному DD, і на ES-UP/«поліглот», скажи
слідкувачу, які адреси — ES-UP (шлях запису відрізняється за протоколом —
дивись [protocol-es-up.uk.md](protocol-es-up.uk.md)):

```bash
# у jbd2mqtt.env — приклад: адреса 1 — ES-UP-пак, адреса 0 — класичний DD
BMS_ESUP_ADDRS=1
```

Лиши `BMS_ESUP_ADDRS` порожнім, якщо в тебе лише паки на класичному DD (або
один пак на адресі 0) — дефолтна поведінка (адреса 0 = класичний DD, усе
інше = ES-UP) не зміниться.

## 8. Калібрування й SOC — спершу читай, потім пиши

Дрейф ємності/SOC між паралельними паками і калібрування датчика струму —
детально, з точними рецептами на рівні регістрів, у
[soc-calibration.uk.md](soc-calibration.uk.md),
[protocol-jbd-dd.uk.md](protocol-jbd-dd.uk.md) і
[protocol-es-up.uk.md](protocol-es-up.uk.md) — прочитай їх ПЕРЕД тим, як щось
писати.

**Правило, що стосується КОЖНОГО запису в цьому тулкіті: зупини демон
`jbd2mqtt` (і `ser2net`, якщо ганяєш приклад з `examples/ser2net/`) ПЕРЕД
читанням чи записом налаштувань руками.** Два процеси, що опитують/пишуть ту
саму RS485-шину одночасно, дають биті/обрізані кадри — у кращому разі
невдалий запис, у гіршому — запис зі сміттям. Піднімай демон назад лише
ПІСЛЯ перевірки зміни:

```bash
sudo systemctl stop jbd2mqtt.service      # або: вбий ручний/передній запуск
python3 src/jbd_settings.py --set 0x2A=3400 --yes     # приклад: напруга старту балансу
sudo systemctl start jbd2mqtt.service
```

## 9. Інтеграція з Home Assistant

MQTT-discovery (крок 5) заводить усі сутності в HA без жодного YAML. Для
автоматизацій поверх цих даних — сторожі напруги комірок, дашборд режиму
балансування, нічна дотяжка — дивись
[home-assistant.uk.md](home-assistant.uk.md) і
готові приклади для адаптації в
[`examples/home-assistant/`](../examples/home-assistant/). Lovelace-картка,
що гарно візуалізує дані по комірках і балансу — в
[`lovelace-card/README.md`](../lovelace-card/README.md).

## 10. Чекліст — перевір, що все працює

- [ ] `python3 src/jbd_bms.py --addr <N>` повертає адекватні дані для
      кожного пака (напруга в районі 30-62 В для 16S LFP, SOC 0-100%).
- [ ] `jbd2mqtt` запущений (`systemctl status jbd2mqtt` = `active`, або
      контейнер `Up`).
- [ ] `mosquitto_sub -t 'deye_bms/#' -v` показує оновлення `state` кожні
      `POLL_INTERVAL` секунд, і `availability` = `online`.
- [ ] Кожен пак зʼявився окремим пристроєм у HA → Devices & Services → MQTT,
      із заповненими сутностями комірок/напруги/струму/температур/балансу
      (не `unknown`/`unavailable`).
- [ ] Якщо увімкнув слідкувач балансування: сенсор «Режим балансування»
      показує `charge` або `static`, не `unknown`, після кількох хвилин
      пака вище напруги старту балансу.
- [ ] `python3 -m pytest tests/ -q` проходить (перевірка на здоровий глузд —
      ці тести не чіпають реальне залізо).

## 11. Оновлення

```bash
cd /opt/jbd-bms-toolkit          # або куди розгорнув
sudo systemctl stop jbd2mqtt.service
git pull
pip install -r requirements.txt --upgrade
sudo systemctl start jbd2mqtt.service
```

Час від часу звіряй `jbd2mqtt.env.example` зі своїм `jbd2mqtt.env` — нові
змінні додаються з безпечними дефолтами, але варто знати, що зʼявилось нове.

## 12. Усунення несправностей

**Взагалі немає відповіді від BMS** (`немає відповіді`/таймаути з
`jbd_bms.py`): перевір полярність A/B (поміняй місцями — найчастіша помилка),
GND, що кабель саме на RS485-розʼємі (не «Parallel»/UART на
багатопортових BMS), і DIP-адресу. Запусти `bms_probe_multi.py`, щоб
виключити розбіжність протоколу/швидкості взагалі.

**Биті/неправдоподібні значення (SOC стрибає на абсурдні числа, напруга поза
30-62 В)**: майже завжди **колізія на спільній шині** — щось інше (ручний
скрипт, `ser2net`, другий екземпляр `jbd2mqtt`) говорить з BMS одночасно.
Переконайся, що порт тримає рівно ОДИН процес. `read_all()` у `jbd_bms.py`
вже відкидає фізично неможливі кадри, а не пропускає їх далі, але якщо це
видно із сирого проб-скана — це проблема контенції шини, не BMS.

**Відповідає не той пак, або пак не відповідає на очікуваній адресі**:
перевір, що DIP-адреса фізично збігається з тим, що в `BMS_ADDRS`/`--addr`.
Деякі «поліглот»-прошивки під час скану відповідають на БУДЬ-ЯКУ ненульову
адресу — якщо паків кілька, перевіряй кожну адресу окремо (крок 3), не
покладайся на те, що DIP-перемикач відпрацьовує точно так, як
задокументовано для твоєї конкретної ревізії прошивки.

**`Permission denied` при відкритті `/dev/ttyUSB0`**: твій користувач (або
`User=` сервісу systemd) не в групі `dialout`:

```bash
sudo usermod -aG dialout <твій-юзер>     # далі релогін, або:
sudo usermod -aG dialout jbd2mqtt         # для користувача сервісу systemd
```

(Наданий `deploy/systemd/jbd2mqtt.service` уже працює з `Group=dialout`, тож
це важливо переважно якщо ганяєш скрипти руками під власним юзером або
правив юніт.)

**HA показує пристрій/сутності як `unavailable`**: перевір власний топік
`availability` демона `jbd2mqtt` і логи
(`journalctl -u jbd2mqtt -f` або stdout при ручному запуску) — міст позначає
пак офлайн після 3 невдач читання поспіль, і весь демон офлайн через LWT,
якщо процес впав зовсім. Серія «немає відповіді» в логу прямо перед тим, як
`availability` падає в offline — це проблема серійного звʼязку (див. вище), а
не MQTT/HA.

**Запис у регістр «не ліг» («прийнято=True», але не закріпився)**: не довіряй
самому підтвердженню прийому — кожен шлях запису в цьому тулкіті перечитує
СВІЖОЮ сесією, щоб верифікувати персист, і скрипти друкують цей результат
прямо (`ЗБЕРЕЖЕНО` / `НЕ ЗБЕРЕГЛОСЯ`). Якщо не закріпилось — майже напевно
демон (чи інший процес) усе ще опитував шину під час запису — зупини його
(крок 8) і повтори.

**`ModuleNotFoundError: No module named 'serial'` / `'paho'`**: ти не в venv,
або пропустив `pip install -r requirements.txt`. Швидкий одноразовий запуск
без встановлення: `uv run --with pyserial --with paho-mqtt python3 src/jbd_bms.py`.
